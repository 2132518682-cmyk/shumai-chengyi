## 二、端侧渲染器技术方案

### 2.1 选型（基于 2026-11 实况核实）

主后端：**three.js r186+ 原生 `GaussianSplat`**（`three/addons/objects/GaussianSplat.js`，仅支持 `WebGPURenderer`）

选它的理由，正好一一对应我们实测出的三个画面病症：

| 我们的病症 | 该方案的内置能力 |
|---|---|
| 形体扭曲/破碎 | GPU 深度排序 |
| 发灰、无高光 | 视相关球谐（SH）全阶着色 |
| 分辨率糊 | WebGPU 管线 + devicePixelRatio 正确缩放 |
| 交互缺失 | 内置 raycasting、逐 mesh 视锥剔除 |

兜底后端：**mkkellogg/GaussianSplats3D**（WebGL2，成熟生态）

必须做兜底的原因：微信内置浏览器、部分旧版 iOS 对 WebGPU 支持不足，而评审大概率是微信扫码打开。检测 `navigator.gpu` 且 adapter 可用 → 走 WebGPU；否则降级 WebGL2，并在页面顶部提示「建议用系统浏览器打开以获得最佳画质」。两套后端共用同一份解码后的属性数据，切换成本低。

不采用的：gsplat.js（生态偏薄）、Spark.js v2.0（面向超大场景 LoD 流式，我们单件文物用不上，徒增复杂度）、SuperSplat（本地已有，仅作渲染对拍参考）。

### 2.2 架构分层

```
cyg-loader（自有解码器）
  .cyg 压缩包 → 解码 → 标准属性数组
    positions(f32) / scales(f32) / quats(f32) / opacity(f32) / SH(f32 或 f16)
        │
        ├─→ three.js GaussianSplat (WebGPU)      ← 主
        └─→ GaussianSplats3D 几何 (WebGL2)        ← 兜底
```

关键：**自研的只有解码器，光栅化交给成熟引擎**。这样压缩研究的产出（自有格式）被完整保留，渲染质量与排序/抗锯齿不承担自研风险。这是本方案把工期从 3–4 周压到 1–2 周的核心决策。

## 三、E24 实验设计（作品的画质底线，必须先跑）

### 3.1 目标

把观感从「勉强」拉回「可用」，同时把体积压到 8–10×。不再以 15× 为目标。

### 3.2 变量

| 变量 | 取值 | 说明 |
|---|---|---|
| 剪枝保留率 | p60 / p70 / p75（对照） | p75 已跑，主要补 p60/p70 |
| 量化档位 | 75B（rest8/dc8/geom32）、69B（+xyz fp16） | 已被 E23b 证明近乎无损，直接用 |
| 浮空高斯阈值 | 无剔除 / opacity<0.005 / opacity<0.01 | 新增变量，专治雾感 |

### 3.3 新增观感指标（本作品的技术亮点之一）

**背景泄漏亮度（Background Leakage, BL）**：取 GT 中亮度 < 0.02 的像素集合，计算渲染结果在该集合上的平均亮度。数值越低说明浮空高斯越少、画面越干净。

理由：PSNR 对「黑背景上飘一层灰雾」极不敏感，这正是 p75 数字尚可但观感崩掉的根源。补这个指标，才能让压缩决策与人的实际感受对齐。

验收双轨：PSNR/SSIM/LPIPS + BL 指标 + 人工渲染图比对，三样都过才算过。

### 3.4 预期产出

| 方案 | 高斯数 | 体积 | 压缩比 | 预期观感 |
|---|---|---|---|---|
| p60 + 75B | 73,717 | 5.53 MB | 7.9× | 明显优于现状 |
| p70 + 75B | 55,288 | 4.15 MB | 10.5× | 优于现状 |
| p75 + 75B（现状） | 46,073 | 3.30 MB | 13.2× | 勉强 |
| p80 + 58B | 36,859 | 2.14 MB | 20.4× | 不可用 |

作品对外主打档位，取「观感过线前提下体积最小」的那一档，由上述实验数据决定，不预设结论。
